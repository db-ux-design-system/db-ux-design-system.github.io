## Drei Zahlen, drei Arten von Änderung

Jede Version hat die Form `MAJOR.MINOR.PATCH` und folgt der **semantischen Versionierung**. Die Zahl, die steigt, zeigt dir, wie viel sich ändert.

<LearnAside>

<img
	src="/assets/documentation/releases/release-types.png"
	alt="Übersicht der semantischen Versionierung: v1.2.3 – Major (Breaking Changes), Minor (neue Features, abwärtskompatibel), Patch (Fehlerbehebungen, keine API-Änderungen)"
	style={{ maxWidth: '100%' }}
/>

| Release | Änderungen                                          | Abwärtskompatibel |
| ------- | --------------------------------------------------- | ----------------- |
| Major   | Breaking Changes in der API oder der Design Library | Nein              |
| Minor   | Neue Features und Verbesserungen                    | Ja                |
| Patch   | Fehlerbehebungen und sehr kleine Verbesserungen     | Ja                |

</LearnAside>

</LearnBlock>

<LearnBlock>

## Design und Entwicklung teilen eine Version

Major- und Minor-Nummer sind in Figma und im Code gleich. Patches werden je Seite getrennt gezählt.

<LearnAside>

Auch wenn nur Design oder nur Entwicklung eine Änderung einführt, steigt die gemeinsame Versionsnummer für beide. So bleiben die Versionen synchron.

</LearnAside>

</LearnBlock>

<LearnBlock>

## Major-Releases bringen Breaking Changes

Ein Major-Release ist nicht abwärtskompatibel, du passt deine Implementierung also an. Major-Releases liegen mindestens 2–3 Monate auseinander und werden vorab angekündigt.

<LearnAside>

Den geplanten Umfang kündigt das Team im Teams-Kanal des DB UX Design Systems an. Zu jedem Major-Release gibt es einen [Migration Guide](/de/dokumentation/releases/migration-guides).

**Beispiele:**

- Eine Überarbeitung der Farbstruktur oder der visuellen Identität
- Umbenannte Einstellungen von Komponenten
- Neue Komponenten, die bestehendes Verhalten ändern

</LearnAside>

</LearnBlock>

<LearnBlock>

## Minor-Releases ergänzen Features in jedem Sprint

Ein Minor-Release ergänzt Features und Verbesserungen, ohne die API zu ändern. Es folgt dem zweiwöchigen Sprint-Rhythmus des Teams.

<LearnAside>

Ein Minor-Release entfällt, wenn keine relevanten Änderungen bereitstehen. Einmal im Monat fasst ein Beitrag im Teams-Kanal alle Releases der vergangenen Wochen zusammen.

**Beispiele:**

- Erweiterungen bestehender Komponenten
- Neue Komponenten ohne Breaking Changes

</LearnAside>

</LearnBlock>

<LearnBlock>

## Patch-Releases beheben Fehler bei Bedarf

Ein Patch-Release enthält Fehlerbehebungen oder sehr kleine Verbesserungen. Es erscheint außerhalb des regulären Rhythmus, wann immer es nötig ist.

<LearnAside>

**Beispiel:** eine Fehlerbehebung an einer Komponente, die keine anderen Features betrifft.

</LearnAside>

</LearnBlock>
