## Du brauchst Node.js 22 und eine IDE mit MCP

Der Server läuft ab **Node.js 22.0.0**. Deine IDE muss das Model Context Protocol (MCP) unterstützen, den Standard, der Agenten mit externen Werkzeugen verbindet.

<LearnAside>

| Anforderung    | Details                                             |
| -------------- | --------------------------------------------------- |
| Node.js        | 22.0.0 oder höher                                   |
| npm            | Bei Node.js enthalten                               |
| MCP-fähige IDE | VS Code, IntelliJ/JetBrains, Cursor, Amazon Q, Kiro |

Der Server funktioniert mit KI-Coding-Agenten wie GitHub Copilot, Amazon Q, Claude und Cursor. Er liest den generierten Quellcode aus den `@db-ux`-Paketen auf npm, damit der Agent die Verwendung von Komponenten nie raten muss.

</LearnAside>

</LearnBlock>

<LearnBlock>

## Registriere den Server in deiner IDE

Ergänze den Eintrag `db-ux` in der MCP-Konfiguration deiner IDE und lege ihn auf die Version deiner `@db-ux`-Pakete fest. Die IDE startet den Server selbst, führe den Befehl also nicht im Terminal aus.

<LearnAside>

### Basiskonfiguration

```json
{
	"mcpServers": {
		"db-ux": {
			"command": "npx",
			"args": ["--yes", "@db-ux/mcp-server"]
		}
	}
}
```

### Version festlegen

Ohne Version lädt `npx --yes` die neueste Version herunter und führt sie ohne Rückfrage aus. Damit du kontrollierst, was in deiner IDE läuft, hänge die Version deiner `@db-ux`-Pakete an den Paketnamen an, zum Beispiel `"@db-ux/mcp-server@<version>"`. Das gilt auch für `@db-ux/agent-cli` im nächsten Schritt.

Du kannst den Server auch als Dev-Dependency in deinem Projekt installieren: `npm i --save-dev @db-ux/mcp-server`.

### Warum nicht im Terminal

Wenn du `npx --yes @db-ux/mcp-server` von Hand ausführst, scheint das Terminal zu hängen. Der Server wartet auf JSON-RPC-Nachrichten über `stdio`, und die schickt nur die IDE.

### VS Code

**Auf Projektebene (empfohlen):** Lege `.vscode/mcp.json` im Projekt-Root an. Diese Datei kannst du über Git teilen.

```json
{
	"servers": {
		"db-ux": {
			"command": "npx",
			"args": ["--yes", "@db-ux/mcp-server"]
		}
	}
}
```

**Auf Nutzerebene:** Ergänze denselben Eintrag unter `mcp` auf der obersten Ebene deiner globalen `settings.json`.

```json
{
	"mcp": {
		"servers": {
			"db-ux": {
				"command": "npx",
				"args": ["--yes", "@db-ux/mcp-server"]
			}
		}
	}
}
```

Wenn beide existieren, hat `.vscode/mcp.json` Vorrang. Eine gelbe Warnung am Key `mcp` ist erwartet – mehr dazu im Schritt zur Fehlerbehebung.

### IntelliJ / JetBrains-IDEs

Öffne _Settings → Tools → AI Assistant → Model Context Protocol (MCP)_, klicke auf _Add (+)_ und trage diese Werte ein:

| Feld      | Wert                      |
| --------- | ------------------------- |
| Name      | `db-ux`                   |
| Type      | `stdio`                   |
| Command   | `npx`                     |
| Arguments | `--yes @db-ux/mcp-server` |

### Amazon Q / Kiro

Amazon Q kann die `CONTEXT.md` deines Projekts als dauerhaften System-Prompt laden. Dann kennt der Agent ab der ersten Nachricht den Server, seine Werkzeuge, die Design Tokens, die Migrations-Workflows und die Komponenten-API. Das verringert erfundene Komponentennamen, Prop-Signaturen und Token-Werte, und neue Teammitglieder bekommen sofort einen Agenten mit vollem Kontext.

1. Öffne oder erstelle `~/.aws/amazonq/agents/default.json`.
2. Ergänze diese Konfiguration:

```json
{
	"agentInstruction": {
		"paths": ["CONTEXT.md"]
	}
}
```

3. Stelle sicher, dass `CONTEXT.md` im Projekt-Root liegt. Die Agent CLI aus dem nächsten Schritt kopiert sie dorthin.

Der Pfad wird relativ zum Workspace-Root aufgelöst. Amazon Q und Kiro lesen die Datei zu Beginn jeder Session und fügen sie als System-Kontext ein.

## Erzeuge die Projektregeln

Die **Agent CLI** schreibt die Regeln für deine installierten `@db-ux`-Pakete in `.github/copilot-instructions.md`. Führe sie im Stammverzeichnis deines Repositorys aus und nach jedem Update des Design Systems erneut.

```shell
npx @db-ux/agent-cli
```

<LearnAside>

Das Werkzeug durchsucht `node_modules` nach installierten `@db-ux`-Paketen und legt die Datei mit der Dokumentation genau dieser Versionen an oder aktualisiert sie. Die Regeln beschreiben, wie Komponenten verwendet und Design Tokens referenziert werden, damit der Agent keine falschen Muster erfindet.

In einem Monorepo gibst du den Ordner an, in dem die Pakete installiert sind:

```shell
npx @db-ux/agent-cli packages/frontend
```

Lege auch hier die Version fest, zum Beispiel `npx @db-ux/agent-cli@<version>`, passend zur Version deiner `@db-ux`-Pakete.

</LearnAside>

</LearnBlock>

## Prüfe die Verbindung

Suche `db-ux` in der Liste der MCP-Server deiner IDE. Bitte dann deinen Agenten, die Komponenten des Design Systems aufzulisten – er sollte mit den echten Komponentennamen antworten.

<LearnAside>

- **Status:** Die IDE zeigt einen grünen Indikator oder den Eintrag `db-ux` in ihrer Liste der MCP-Server
- **Logs:** Wenn der Server nicht erscheint, öffne die MCP-Output-Logs, in VS Code zum Beispiel unter _Output Panel_ → _MCP_ oder _MCP Servers_

</LearnAside>

## Werkzeuge liefern Fakten, Prompts steuern Abläufe

**Werkzeuge** geben dem Agenten Fakten wie Komponenten, Props, Beispiele, Tokens und Icons. **Prompts** verbinden diese Werkzeuge zu Abläufen für Seitengerüste, Migration, Code-Review und Audits der Barrierefreiheit.

<LearnAside>

### Werkzeuge für Discovery

| Werkzeug                | Beschreibung                                                                                                                           |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `list_components`       | Gibt alle verfügbaren Komponentennamen zurück (z. B. `button`, `input`, `tag`). Immer zuerst aufrufen.                                 |
| `get_component_props`   | Gibt den rohen TypeScript-Inhalt der `model.ts` zurück – alle Interfaces, Prop-Typen und JSDoc-Kommentare.                             |
| `get_component_details` | Listet die verfügbaren Beispielnamen einer Komponente auf (z. B. `"Variant"`, `"Show Icon Leading"`).                                  |
| `get_example_code`      | Gibt den exakten generierten Quellcode eines Beispiels für ein Framework zurück (`react`, `angular`, `vue`, `web-components`, `html`). |

### Werkzeuge für Tokens und Assets

| Werkzeug                       | Beschreibung                                                                                                                                          |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `get_design_tokens`            | Gibt CSS Custom Properties (`--db-*`) für eine Token-Kategorie zurück. Spacing, Elevation und Density liefern kompilierte Werte.                      |
| `list_design_token_categories` | Listet alle Token-Kategorien auf (z. B. `colors`, `spacing`, `typography`, `elevation`, `density`).                                                   |
| `list_icons`                   | Gibt alle gültigen Icon-Namen zurück. Immer aufrufen, bevor eine `icon`-Property gesetzt wird.                                                        |
| `list_visuals`                 | Gibt alle Namen visueller Referenzen zurück (z. B. `dashboard`, `form`, `table`). Vor `get_visual_reference` aufrufen.                                |
| `get_visual_reference`         | Gibt eine visuelle Referenz (max. 800 × 800 px, JPEG-Qualität 75) als Base64 zurück. Nur nutzen, wenn visueller Kontext nötig ist, z. B. bei Layouts. |
| `docs_search`                  | Durchsucht die Dokumentation (Richtlinien, Barrierefreiheit, Migration). Dient dem Agenten als Suchquelle für Antworten (RAG).                        |

### Werkzeuge für die Migration

| Werkzeug                      | Beschreibung                                                                                                                                                                                                                                                            |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scan_generation_2_migration` | Bei Migrationen zuerst aufrufen. Durchsucht eine Datei nach Mustern aus Generation 2 (Klassen `cmp-*`, `elm-*` und `rea-*`, Web Components `<db-*>`, Tokens `db-color-*`, alte Icon-Namen) und gibt einen JSON-Report mit Zeilennummern und Migrationshinweisen zurück. |
| `list_migration_guides`       | Gibt alle verfügbaren Migration Guides zurück (z. B. `color-migration`, `component-migration`).                                                                                                                                                                         |
| `get_migration_guide`         | Gibt den vollständigen Markdown-Inhalt eines Migration Guides zurück.                                                                                                                                                                                                   |
| `verify_migrated_code`        | Speichert generierten Code temporär und prüft ihn mit `tsc --noEmit`. Gibt bei Fehlern Diagnostics zurück (max. 3 Versuche).                                                                                                                                            |

### Beispiel: ein React Button

```text
list_components          → bestätigt, dass "button" existiert
get_component_props      → zeigt DBButtonProps, Varianten, Typen
get_component_details    → listet ["Density", "Variant", "Show Icon Leading", ...]
get_example_code         → gibt den Quellcode von show-icon-leading.example.tsx zurück
list_icons               → bestätigt, dass "arrow_right" ein gültiger Icon-Name ist
get_design_tokens        → gibt --db-spacing-fixed-md für das Layout zurück
verify_migrated_code     → prüft den generierten Code via tsc --noEmit
```

### Prompts

Du startest Prompts im Chat deiner IDE, wenn sie MCP-Prompts unterstützt, oder im MCP Inspector.

**`scaffold_page`** erzeugt die Grundstruktur einer Seite oder eines komplexen Moduls.

| Parameter                 | Beschreibung                               |
| ------------------------- | ------------------------------------------ |
| `page_type`               | Art der Seite (z. B. `dashboard`, `form`)  |
| `framework`               | Ziel-Framework (`react`, `angular`, `vue`) |
| `additional_requirements` | Optionale zusätzliche Anforderungen        |

**`migrate_component`** überführt Legacy-Code (Bootstrap, natives HTML, DB UI v1/v2) in Generation 3. Der Prompt verbindet zwölf Werkzeuge in fünf verpflichtenden Schritten und korrigiert sich mit einer Compiler-Prüfung selbst.

| Parameter          | Erforderlich | Beschreibung                                                        |
| ------------------ | ------------ | ------------------------------------------------------------------- |
| `legacy_code`      | Ja           | Der zu migrierende Quellcode (max. 10.000 Zeichen)                  |
| `source_context`   | Ja           | Herkunft: `db-ui-v1`, `db-ui-v2`, `bootstrap-4`, `native-html` usw. |
| `target_framework` | Ja           | Ziel: `react`, `angular`, `vue`, `web-components`, `html`           |

```text
Schritt 0: scan_generation_2_migration → Datei-Scan (deterministisch, kein Raten)
Schritt 1: Migrations-Analyse     → Mapping-Tabelle: Legacy → DB UX v3
Schritt 2: Component Discovery    → Props, Beispiele, Tokens, Icons laden
Schritt 3: Code-Generierung       → vollständig migrierter Code (intern)
Schritt 4: verify_migrated_code   → Compiler-Prüfung + Selbstkorrektur (max. 3×)
Schritt 5: Finale Ausgabe         → ✅ VERIFIED oder ⚠️ WARNING + Diagnostics
```

**`review_ui_code`** prüft einen Code-Ausschnitt streng auf Qualität, Barrierefreiheit und Konformität mit dem Design System.

**`audit_accessibility`** prüft einen Code-Ausschnitt gegen WCAG 2.2 AA. Der Prompt bewertet interaktive Patterns und die Fokusreihenfolge und erzeugt manuelle Testskripte für die Qualitätssicherung.

Beide erwarten dieselben Parameter:

| Parameter      | Beschreibung                   |
| -------------- | ------------------------------ |
| `code_snippet` | Der zu prüfende Quellcode      |
| `framework`    | Framework des Code-Ausschnitts |

## Wenn der Server nicht antwortet

Die meisten Probleme entstehen durch die Konfiguration der IDE oder durch npm-Workspaces in einem Monorepo. Der **MCP Inspector** testet Werkzeuge und Prompts ohne deine IDE.

<LearnAside>

| Symptom                                                      | Ursache und Lösung                                                                                                                         |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Gelbe Warnung „Unknown Configuration Setting“ am Key `mcp`   | Standard-VS-Code kennt den Key nicht. Das ist erwartet. Solange dein MCP-Client (Copilot Chat, Cursor) aktiv ist, funktioniert der Server. |
| `npx @db-ux/mcp-server` schlägt im Root eines Monorepos fehl | Die Auflösung der npm-Workspaces stört. Starte stattdessen den lokalen Build mit `node`, wie unten gezeigt.                                |
| Das Terminal hängt nach `npx --yes @db-ux/mcp-server`        | Der Server wartet auf die IDE. Beende den Befehl und lass die IDE den Server starten.                                                      |
| Der Server fehlt in der Liste der IDE                        | Sieh in die MCP-Output-Logs deiner IDE.                                                                                                    |

### Server im Root eines Monorepos starten

Führe zuerst `npm run build` im Verzeichnis `mcp-server` aus. Verweise dann in der Konfiguration auf den lokalen Build:

```json
{
	"db-ux": {
		"command": "node",
		"args": ["packages/mcp-server/dist/index.js"]
	}
}
```

### Mit dem MCP Inspector testen

Der MCP Inspector ist das offizielle Werkzeug, um MCP-Werkzeuge und Prompts unabhängig von der IDE zu prüfen.

```bash
cd packages/mcp-server && npm run build
npx @modelcontextprotocol/inspector --transport stdio node dist/index.js
```

1. Führe die Befehle aus. Der Inspector startet einen lokalen Webserver.
2. Öffne die vollständige URL inklusive Token im Browser (z. B. `http://localhost:6274/?MCP_PROXY_AUTH_TOKEN=...`).
3. Klicke auf „Connect“.
4. Rufe im Tab „Tools“ einzelne Werkzeuge auf und prüfe die Antworten.
5. Teste im Tab „Prompts“ Prompts wie `scaffold_page`.

Der Inspector nutzt Port 6274 für die UI und Port 6277 für den Proxy. Wenn sie belegt sind, gibst du sie mit `lsof -ti :6274 -ti :6277 | xargs kill -9` frei.
