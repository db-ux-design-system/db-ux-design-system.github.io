## You need Node.js 22 and an IDE with MCP

The server runs on **Node.js 22.0.0 or higher**. Your IDE must support the Model Context Protocol (MCP), the standard that connects agents to external tools.

<LearnAside>

| Requirement     | Details                                             |
| --------------- | --------------------------------------------------- |
| Node.js         | 22.0.0 or higher                                    |
| npm             | Bundled with Node.js                                |
| MCP-capable IDE | VS Code, IntelliJ/JetBrains, Cursor, Amazon Q, Kiro |

The server works with agents such as GitHub Copilot, Amazon Q, Claude and Cursor. It reads the generated source code shipped in the `@db-ux` npm packages, so the agent never has to guess component usage.

</LearnAside>

</LearnBlock>

## Register the server in your IDE

Add the `db-ux` entry to the MCP configuration of your IDE and pin it to the version of your `@db-ux` packages. The IDE starts the server itself, so do not run the command in a terminal.

<LearnAside>

### Base configuration

```json
{
	"mcpServers": {
		"db-ux": {
			"command": "npx",
			"args": ["--yes", "@db-ux/mcp-server"]
		}
	}
}
```

### Pin the version

Without a version, `npx --yes` downloads the latest release and runs it without asking. To control what runs in your IDE, append the version of your `@db-ux` packages to the package name, for example `"@db-ux/mcp-server@<version>"`. The same applies to `@db-ux/agent-cli` in the next step.

You can also install the server as a dev dependency of your project: `npm i --save-dev @db-ux/mcp-server`.

### Why not in the terminal

If you run `npx --yes @db-ux/mcp-server` manually, the terminal appears to hang. The server waits for JSON-RPC messages over `stdio`, which only the IDE sends.

### VS Code

**Project level (recommended):** create `.vscode/mcp.json` in the project root. You can share this file via Git.

```json
{
	"servers": {
		"db-ux": {
			"command": "npx",
			"args": ["--yes", "@db-ux/mcp-server"]
		}
	}
}
```

**User level:** add the same entry under `mcp` at the root of your global `settings.json`.

```json
{
	"mcp": {
		"servers": {
			"db-ux": {
				"command": "npx",
				"args": ["--yes", "@db-ux/mcp-server"]
			}
		}
	}
}
```

If both exist, `.vscode/mcp.json` takes precedence. A yellow warning on the `mcp` key is expected – see the troubleshooting step.

### IntelliJ / JetBrains IDEs

Open _Settings → Tools → AI Assistant → Model Context Protocol (MCP)_, click _Add (+)_ and enter these values:

| Field     | Value                     |
| --------- | ------------------------- |
| Name      | `db-ux`                   |
| Type      | `stdio`                   |
| Command   | `npx`                     |
| Arguments | `--yes @db-ux/mcp-server` |

### Amazon Q / Kiro

Amazon Q can load the `CONTEXT.md` of your project as a persistent system prompt. The agent then knows the server, its tools, the design tokens, the migration workflows and the component API from the first message on. This reduces invented component names, prop signatures and token values, and new team members get a context-aware agent right away.

1. Open or create `~/.aws/amazonq/agents/default.json`.
2. Add this configuration:

```json
{
	"agentInstruction": {
		"paths": ["CONTEXT.md"]
	}
}
```

3. Make sure `CONTEXT.md` is in the project root. The Agent CLI from the next step copies it there.

The path is resolved relative to the workspace root. Amazon Q and Kiro read the file at the start of every session and inject it as system-level context.

</LearnAside>

## Generate the project rules

The **Agent CLI** writes the rules for your installed `@db-ux` packages into `.github/copilot-instructions.md`. Run it in the root of your repository and again after every update of the design system.

```shell
npx @db-ux/agent-cli
```

<LearnAside>

The tool scans `node_modules` for installed `@db-ux` packages and creates or updates the file with the documentation for exactly those versions. The rules cover component usage and how to reference design tokens, so the agent does not invent usage patterns.

In a monorepo, pass the folder where the packages are installed:

```shell
npx @db-ux/agent-cli packages/frontend
```

Pin the version here as well, for example `npx @db-ux/agent-cli@<version>`, with the version of your `@db-ux` packages.

</LearnAside>

</LearnBlock>

## Check the connection

Look for `db-ux` in the list of MCP servers of your IDE. Then ask your agent to list the components of the design system – it should answer with the real component names.

<LearnAside>

- **Status:** the IDE shows a green indicator or the entry `db-ux` in its MCP server list.
- **Logs:** if the server does not appear, open the MCP output logs, for example in VS Code under _Output Panel_ → _MCP_ or _MCP Servers_.

</LearnAside>

## Tools deliver facts, prompts run workflows

**Tools** give the agent facts such as components, props, examples, tokens and icons. **Prompts** combine these tools into workflows for scaffolding, migration, code review and accessibility audits.

<LearnAside>

### Discovery tools

| Tool                    | Description                                                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `list_components`       | Returns all available component names (e.g. `button`, `input`, `tag`). Always call first.                                    |
| `get_component_props`   | Returns the raw TypeScript `model.ts` content – all interfaces, prop types and JSDoc comments.                               |
| `get_component_details` | Lists the available example names for a component (e.g. `"Variant"`, `"Show Icon Leading"`).                                 |
| `get_example_code`      | Returns the exact generated source code of an example for a framework (`react`, `angular`, `vue`, `web-components`, `html`). |

### Token and asset tools

| Tool                           | Description                                                                                                                              |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `get_design_tokens`            | Returns CSS custom properties (`--db-*`) for a token category. Spacing, elevation and density return compiled values.                    |
| `list_design_token_categories` | Lists all token categories (e.g. `colors`, `spacing`, `typography`, `elevation`, `density`).                                             |
| `list_icons`                   | Returns all valid icon names. Always call before setting an `icon` prop.                                                                 |
| `list_visuals`                 | Returns all visual reference names (e.g. `dashboard`, `form`, `table`). Call before `get_visual_reference`.                              |
| `get_visual_reference`         | Returns a visual reference image (max. 800 × 800 px, JPEG quality 75) as Base64. Use it only when you need visual context, e.g. layouts. |
| `docs_search`                  | Searches the documentation (guidelines, accessibility, migration). Works as a retrieval engine for the agent (RAG).                      |

### Migration tools

| Tool                          | Description                                                                                                                                                                                                                                |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `scan_generation_2_migration` | Call first for migrations. Scans a file for Generation 2 patterns (`cmp-*`, `elm-*` and `rea-*` classes, `<db-*>` Web Components, `db-color-*` tokens, legacy icon names) and returns a JSON report with line numbers and migration hints. |
| `list_migration_guides`       | Returns all available migration guides (e.g. `color-migration`, `component-migration`).                                                                                                                                                    |
| `get_migration_guide`         | Returns the full Markdown content of a migration guide.                                                                                                                                                                                    |
| `verify_migrated_code`        | Saves generated code temporarily and checks it with `tsc --noEmit`. Returns diagnostics on errors (max. 3 attempts).                                                                                                                       |

### Example: a React button

```text
list_components          → confirms "button" exists
get_component_props      → shows DBButtonProps, variants, types
get_component_details    → lists ["Density", "Variant", "Show Icon Leading", ...]
get_example_code         → returns show-icon-leading.example.tsx source code
list_icons               → confirms "arrow_right" is a valid icon name
get_design_tokens        → returns --db-spacing-fixed-md for layout
verify_migrated_code     → checks generated code via tsc --noEmit
```

### Prompts

You start prompts in the chat of your IDE, if it supports MCP prompts, or in the MCP Inspector.

**`scaffold_page`** generates the initial structure of a page or a complex module.

| Parameter                 | Description                                  |
| ------------------------- | -------------------------------------------- |
| `page_type`               | Type of page (e.g. `dashboard`, `form`)      |
| `framework`               | Target framework (`react`, `angular`, `vue`) |
| `additional_requirements` | Optional additional requirements             |

**`migrate_component`** transforms legacy code (Bootstrap, native HTML, DB UI v1/v2) into Generation 3. It combines 12 tools in five mandatory steps and corrects itself with a compiler check.

| Parameter          | Required | Description                                                        |
| ------------------ | -------- | ------------------------------------------------------------------ |
| `legacy_code`      | Yes      | The source code to migrate (max. 10,000 characters)                |
| `source_context`   | Yes      | Origin: `db-ui-v1`, `db-ui-v2`, `bootstrap-4`, `native-html`, etc. |
| `target_framework` | Yes      | Target: `react`, `angular`, `vue`, `web-components`, `html`        |

```text
Step 0: scan_generation_2_migration → file scan (deterministic, no guessing)
Step 1: Migration Analysis      → mapping table: Legacy → DB UX v3
Step 2: Component Discovery     → load props, examples, tokens, icons
Step 3: Code Generation         → complete migrated code (internal)
Step 4: verify_migrated_code    → compiler check + self-correction (max 3×)
Step 5: Final Output            → ✅ VERIFIED or ⚠️ WARNING + diagnostics
```

**`review_ui_code`** runs a strict audit of quality, accessibility and design system compliance on a code snippet.

**`audit_accessibility`** checks a code snippet against WCAG 2.2 AA. It evaluates interactive patterns and focus order and generates manual test scripts for QA.

Both take the same parameters:

| Parameter      | Description                        |
| -------------- | ---------------------------------- |
| `code_snippet` | The source code to review or audit |
| `framework`    | Framework of the snippet           |

## If the server does not respond

Most problems come from the IDE configuration or from npm workspaces in a monorepo. The **MCP Inspector** tests tools and prompts without your IDE.

<LearnAside>

| Symptom                                                 | Cause and fix                                                                                                                    |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Yellow "Unknown Configuration Setting" warning on `mcp` | Standard VS Code does not know the key. This is expected. As long as your MCP client (Copilot Chat, Cursor) is active, it works. |
| `npx @db-ux/mcp-server` fails from a monorepo root      | npm workspace resolution gets in the way. Start the local build with `node` instead, as shown below.                             |
| The terminal hangs after `npx --yes @db-ux/mcp-server`  | The server waits for the IDE. Stop the command and let the IDE start the server.                                                 |
| The server is missing from the IDE list                 | Check the MCP output logs of your IDE.                                                                                           |

### Start the server from a monorepo root

Run `npm run build` in the `mcp-server` directory first. Then point the configuration to the local build:

```json
{
	"db-ux": {
		"command": "node",
		"args": ["packages/mcp-server/dist/index.js"]
	}
}
```

### Test with the MCP Inspector

The MCP Inspector is the official tool to validate MCP tools and prompts independently of your IDE.

```bash
cd packages/mcp-server && npm run build
npx @modelcontextprotocol/inspector --transport stdio node dist/index.js
```

1. Run the commands. The inspector starts a local web server.
2. Open the full URL including the token in your browser (e.g. `http://localhost:6274/?MCP_PROXY_AUTH_TOKEN=...`).
3. Click "Connect".
4. In the "Tools" tab, call single tools and inspect the responses.
5. In the "Prompts" tab, test prompts such as `scaffold_page`.

The inspector uses port 6274 for the UI and port 6277 for the proxy. If they are occupied, free them with `lsof -ti :6274 -ti :6277 | xargs kill -9`.
