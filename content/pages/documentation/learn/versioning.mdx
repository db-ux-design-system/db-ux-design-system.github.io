## Three numbers, three kinds of change

Every version has the form `MAJOR.MINOR.PATCH`, following **Semantic Versioning**. The number that goes up tells you how much changes.

<LearnAside>

<img
	src="/assets/documentation/releases/release-types.png"
	alt="Semantic Versioning overview: v1.2.3 – Major (breaking changes), Minor (new features, backward-compatible), Patch (bug fixes, no API changes)"
	style={{ maxWidth: '100%' }}
/>

| Release | Changes                                       | Backward-compatible |
| ------- | --------------------------------------------- | ------------------- |
| Major   | Breaking Changes in the API or design library | No                  |
| Minor   | New features and improvements                 | Yes                 |
| Patch   | Bug fixes and very small improvements         | Yes                 |

</LearnAside>

</LearnBlock>

<LearnBlock>

## Design and development share one version

The Major and Minor numbers are the same in Figma and in code. Patches are counted separately for each side.

<LearnAside>

If only design or only development introduces a change, the shared version number still goes up for both. This keeps the versions in sync.

</LearnAside>

</LearnBlock>

<LearnBlock>

## Major releases bring Breaking Changes

A Major release is not backward-compatible, so you adapt your implementation. Major releases are planned at least 2–3 months apart and announced in advance.

<LearnAside>

The planned scope is announced in the Teams channel of the DB UX Design System. Each Major release comes with a [Migration Guide](/documentation/releases/migration-guides).

**Examples:**

- An overhaul of the color structure or the visual identity
- Renamed component settings
- New components that change existing behavior

</LearnAside>

</LearnBlock>

<LearnBlock>

## Minor releases add features every sprint

A Minor release adds features and improvements without changing the API. It follows the two-week sprint cycle of the team.

<LearnAside>

A Minor release is skipped if no relevant changes are ready. Once a month, a summary post in the Teams channel covers all releases of the past weeks.

**Examples:**

- Enhancements to existing components
- New components without Breaking Changes

</LearnAside>

</LearnBlock>

<LearnBlock>

## Patch releases fix bugs when needed

A Patch release contains bug fixes or very small improvements. It ships outside the regular cadence, whenever it is needed.

<LearnAside>

**Example:** a bug fix for a component that has no impact on other features.

</LearnAside>

</LearnBlock>
